# 代码知识图谱业务语义

以下规则只解释当前 Schema 已观察到的结构。生成 Cypher 时必须同时遵守动态 Schema 中的标签、属性、关系方向和用户要求的返回形状，不能根据本说明虚构图结构。

## 锚点、归属与版本

- `方法`、`类`、`微服务`的归属链固定为：`方法-[:归属于]->类-[:归属于]->微服务`。题目给出 `AdminRouteServiceImpl` 这类不含包名的短类名时只能用 `类.简名 = 'AdminRouteServiceImpl'` 或 `方法.所属类名 ENDS WITH '.AdminRouteServiceImpl'` 定位，禁止把短类名当成 `类.全限定名` 的完整值；完整方法名才使用 `方法.全限定名`。`Class.method` 必须同时约束方法名与所属类，不能猜测唯一实现。
- 题目给出 `ts-...-service` 形式的服务名称时，必须用 `(service:微服务 {服务名称: 'ts-...-service'})` 锚定，并沿归属链查找方法或类；禁止拿服务名称与 `方法.全限定名`、`方法.所属类名` 或类名比较。服务归属结果统一投影 `service.服务名称 AS 服务名称`，除非题目明确要求“上游服务”或“下游服务”等角色列名。
- `类-[:接口实现]->类` 的起点是实现类、终点是接口。查询实现类时返回起点，查询接口时返回终点。
- 题目只说“声明方法”而未明确只要短方法名时，投影 `方法.全限定名 AS 方法全限定名`；只有明确要求“方法名和方法签名”时才投影 `方法.方法名 AS 方法名, 方法.方法签名 AS 方法签名`。
- 当前问题包含多个独立匹配片段时，使用节点或关系的 `图谱版本` 相等条件避免未来跨版本组合；不要硬编码具体版本值。

## 上游 API 与 REST 出口

- 上游入口固定为 `方法-[:服务于]->上游API`。API 路径来自 `上游API.API路径`，HTTP 方法来自 `上游API.HTTP方法`；服务公开 API 从目标服务反向经过类和方法，再沿 `服务于` 到上游 API。
- 从某个类推导所属服务后查询“该服务的全部公开 API”必须分成两个匹配阶段：先 `(anchor:类)-[:归属于]->(service:微服务)`，再从 `(service)<-[:归属于]-(:类)<-[:归属于]-(method:方法)-[:服务于]->(api:上游API)` 重新匹配该服务全部方法。第二阶段不得继续用 anchor 类名限制 `method`，否则只会得到该实现类自身直接服务的 API，通常为空。
- REST 出口固定为 `方法-[:下游调用]->下游API`。目标服务使用 `下游API-[:目标服务]->微服务`；目标入口映射使用 `下游API-[:外部调用]->上游API`，入口方法再通过 `方法-[:服务于]->上游API` 取得。
- `目标服务` 和 `外部调用` 可能缺失。完整 REST 明细必须保留已确认的调用方法和下游 API，并用 `OPTIONAL MATCH` 补充目标服务、目标上游 API、入口方法和匹配类型，不能因可选映射缺失过滤主结果。
- API 反向的 `归属于` 与 `服务于`、`下游调用` 表达同一归属事实；一个查询只选择一套清晰方向，不能同时展开两套边造成重复计数。

## 直接调用、可达集合与有序路径

- `方法-[:接口调用]->方法` 表示 Controller 或接口入口方法分派到实现方法；关系的 `经由接口` 保存接口全限定名。
- `方法-[:调用]->方法` 是预计算可达关系，不是相邻边。普通直接调用过滤 `调用深度=1`；包含接口分派镜像的全部直接代码调用过滤 `调用深度 IN [0,1]`；上游或下游可达方法集合只匹配一条 `调用` 并按题目范围过滤 `调用深度`。过滤属性必须来自已命名的关系变量，例如 `(upstream)-[call:调用]->(target) WHERE call.调用深度 IN [0,1]`，绝不能从方法节点读取 `调用深度`。
- 禁止对 `调用` 使用可变长度遍历。直接上游调用者的唯一方向是 `(upstream:方法)-[call:调用]->(target:方法)`；直接下游被调用者的唯一方向是 `(target:方法)-[call:调用]->(downstream:方法)`，两者不得反转。询问“直接上游”时必须过滤 `call.调用深度 IN [0,1]`。
- 可达入口 API 必须先绑定 `(entry:方法)-[:服务于]->(api:上游API)`，再用 `entry = target OR EXISTS { MATCH (entry)-[reach:调用]->(target) ... }` 判断入口是否能到达目标；只查询 `target-[:服务于]->api` 会漏掉间接入口。
- 有序普通方法路径使用 `链中下一节点`。同一路径中的每条关系必须具有相同 `路径签名`，相邻关系的 `位置索引` 必须连续；最终用 `nodes(path)` 投影有序方法列表。
- 完整入口链可以是目标方法自身、一次 `接口调用`、一段 `链中下一节点`，或先一次 `接口调用` 再接有序普通路径。必须用保持同一返回列形状的 `UNION` 分支表达这些路径，不得用方向不明的 `OPTIONAL MATCH` 和 `CASE` 拼接伪路径。
- 完整下游链必须用 `UNION` 分开“目标方法直接 REST 出口”和“沿有序路径到达 REST 出口”两种形状，并在每个分支完整投影 `目标方法`、`方法路径`、`下游API`、`下游服务`、`目标上游API`、`目标入口方法`。`目标服务`、`外部调用` 与目标入口仍使用 `OPTIONAL MATCH`，不得因映射缺失删除主结果，也不得把目标方法误命名为入口方法。

## MQ 与调用点

- 详细消息路径固定为：`发布方法-[:发布至]->消息交换机-[:路由至]->消息队列-[:消费自]->消费方法`。注意 `消费自` 的方向是消息队列指向消费方法。
- 完整发布或消费路径必须绑定 `发布至.路由键 = 路由至.路由键`，否则共享交换机会把无关发布方法与队列组合。
- 发送服务从发布方法的 `方法→类→微服务` 归属链取得，接收服务从消费方法的归属链取得；不得从共享交换机或队列归属推断发送方或接收方。
- 服务级 MQ 依赖直接使用 `微服务-[:消息依赖]->微服务`。只问队列消费者时从队列沿一跳 `消费自` 查询，不额外引入发布方。
- 发布调用点通过发布方法归属的 `调用点` 及 `发布至.调用点标识 = 调用点.语句文本` 关联；返回调用点时保持发布方法、路由键、交换机和源码位置逐行对应。

## 返回列、聚合与拆分

- 题目要求“接口路径”时投影 `API路径 AS 接口路径`，要求“请求方式”时投影 `HTTP方法 AS 请求方式`；服务归属投影 `微服务.服务名称 AS 服务名称`，目标服务投影 `微服务.服务名称 AS 下游服务`。不要只返回整个节点，也不要擅自改成新的泛化列名。
- REST 来源服务明细必须从调用方法沿 `(caller_method:方法)-[:归属于]->(:类)-[:归属于]->(caller_service:微服务)` 取得，并投影 `caller_service.服务名称 AS 调用服务`；`方法.所属类名` 是类名，绝不是服务名称。按目标服务查询其 REST 上游关联时必须同时返回该调用方服务。服务级 REST 调用数量统一对 `下游调用` 关系计数，并投影 `count(DISTINCT remote) AS 调用关系数`。
- MQ 角色列必须显式命名：消息发送方投影 `sender.服务名称 AS 发送服务`，接收方投影 `receiver.服务名称 AS 接收服务`；不能用无角色的 `服务名称` 代替题目要求的发送或接收服务列。
- 多列 API、REST、调用链和 MQ 结果表示逐行对应的事实，必须在一个结果集中完整投影；不得把方法、API、服务、交换机或队列拆成无法恢复配对的独立结果。
- 非聚合实体或路径查询最终使用 `RETURN DISTINCT`。聚合必须保留题目要求的全部分组列，并对正确的实体或关系计数。
- 只要同一道方法变更题同时要求“全部上游方法”“可达入口 API”“变更方法直接 REST 下游”这三个集合，无论是否出现“分别”二字，都必须拆成三个独立且重复方法锚点的子问题；禁止合并为一个 Cypher。完整调用链或完整消息路径则必须保留为单一子问题。
- 方法变更语境中的泛称“外部服务”固定解释为该变更方法通过 `下游调用→目标服务` 直接访问的下游服务，不是通过 `调用` 关系找到的上游调用方所属服务；对应子问题必须写明“变更方法直接远程调用的下游服务”。

## 废弃模型

- 不得使用旧标签 `API端点`，不得使用旧属性 `API类型`、`接口路径`、`请求方式`、`目标微服务`。
- 不得使用旧关系 `消息流`，不得使用 `消息流类型` 或 `调用类型` 过滤当前关系。

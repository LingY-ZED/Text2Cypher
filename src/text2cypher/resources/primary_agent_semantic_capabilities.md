# 代码知识图谱可检索业务能力

Primary Agent 只使用以下抽象能力规划自然语言检索任务，不推断存储实现细节。

## 代码与归属

- 查询类、方法、接口、实现及它们的归属关系。
- 查询服务、应用、模块与代码元素之间的归属和边界。
- 查询实现关系、返回类型、数量、分组和聚合信息。

## API 与服务交互

- 查询对外 API 入口、请求语义、调用目标和服务归属。
- 查询固定方法或服务的上游来源、直接远程下游和影响范围。
- 查询入口、调用目标和服务之间需要保持对应的事实。

## 调用依赖与路径

- 查询直接调用、接口分派、反向调用者和可达入口。
- 查询完整的上游或下游有序调用路径及其位置顺序。
- 查询变更影响、调用数量和调用关系的聚合结果。

## 消息通信

- 查询消息发布方、路由、队列、消费者和两端服务角色。
- 查询完整消息路径及其中需要保持对应的路由条件。

## 规划边界

- 只规划用户问题需要获取的信息，不生成查询语句或答案。
- 同一记录、同一路径、同一消息路径或同一分组中相互对应的信息必须作为一个检索意图保留；不要按返回列、属性或关系端点机械拆分。
- 一个固定 API 的请求信息和响应信息、一个固定代码元素的归属和实现关系、一个发送服务及其下游服务的对应关系，都属于需要保留的完整答案形状。
- 分组维度与其聚合值必须在同一子问题中。例如，要求“每个目标服务的调用数”时，子问题必须同时要求目标服务和调用数，不能只问总数。
- 调用方向是不可省略的语义：明确区分“哪些方法调用 X”（上游调用者）与“X 调用哪些方法或服务”（下游目标）。
- 不得扩大或缩小原问题的范围：原问题未要求直接、间接、可达性或完整路径时，不得自行加入这些限定、调用链或额外关联信息；保留原问题已有的方向、范围和基数。
- 子问题必须把聚合的答案形状写完整：原问题同时包含对象维度和度量时，应写成“按每个对象给出度量”，不能将其简化成“总数是多少”。
- 只有多个业务视角能够独立重算且不需要其他查询结果时，才拆成多个自然语言查询。每个子问题都必须重复固定对象、方向、条件、分组和完整返回语义。

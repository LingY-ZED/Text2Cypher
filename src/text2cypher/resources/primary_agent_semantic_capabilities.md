# 代码知识图谱可检索业务能力

Primary Agent 只使用以下抽象能力规划自然语言检索任务，不推断存储实现细节。

## 代码与归属

- 查询类、方法、接口、实现及它们的归属关系。
- 查询服务、应用、模块与代码元素之间的归属和边界。
- 查询实现关系、返回类型、数量、分组和聚合信息。

## API 与服务交互

- 查询对外 API 入口、请求语义、调用目标和服务归属。
- 查询固定方法或服务的上游来源、直接远程下游和影响范围。
- 查询入口、调用目标和服务之间需要保持对应的事实。

## 调用依赖与路径

- 查询直接调用、接口分派、反向调用者和可达入口。
- “上游方法”“上游调用方”“上游影响范围”表示目标方法的所有上游可达方法及最短调用距离，不表示完整入口路径。
- 无修饰或明确要求“完整”的“某方法的上游调用链”表示从入口 API / 入口方法经过有序方法路径到达目标方法的完整入口链，不得规划为上游可达方法集合。
- “A 到 B 的调用路径”“A 到 B 的调用顺序”表示两个明确方法锚点之间的有序方法路径；只有明确要求“直接上游”时才限制为直接调用。
- 查询完整的上游或下游有序调用路径及其位置顺序。
- 无方向的“某方法的调用链”“完整调用链”或“端到端调用链”表示以固定方法或入口为根，必须拆成服务内、REST、MQ 三个独立查询。三个查询都从原始锚点重新匹配，不消费其他查询结果，也不表示上游可达集合。
- 查询变更影响、调用数量和调用关系的聚合结果。

### 调用类查询形状

- `direct_upstream`：只查询直接调用锚点方法的上一跳方法。
- `upstream_reachability`：查询所有能够调用到锚点方法的上游方法及最短调用距离；适用于“上游方法”“上游调用方”和“上游影响范围”，不适用于“上游调用链”。
- `direct_downstream_method`：只查询锚点方法直接调用的下一跳方法，不包含远程 REST 出口。
- `ordered_method_path`：查询两个明确方法锚点之间的一条或多条有序方法路径，必须保留路径内的方法顺序和同一路径对应关系。
- `reachable_entry_api`：查询能够到达锚点方法的入口 API 集合，不返回完整的逐跳入口路径。
- `full_entry_chain`：查询入口 API / 入口方法到锚点方法的完整有序链；“某方法的上游调用链”固定使用此形状，并且必须作为一个查询意图保留。
- `direct_rest_egress`：查询锚点方法直接发出的 REST 下游及跨服务信息。
- `full_downstream_chain`：查询从锚点方法到 REST 出口的完整有序下游链，必须作为一个查询意图保留。
- `full_method_call_chain`：仅用于识别原始完整调用链意图；规划结果必须固定拆成三个 `general` 查询，顺序为服务内调用明细、最多两层 REST 跨服务明细、最多一层 MQ 发布消费明细。每条查询必须重复原始锚点和显式限定。

规划每个调用类查询时必须明确固定锚点、上游或下游方向、direct / reachable / ordered path / full chain 范围、查询目标、是否需要入口 API 或 REST 跨服务信息，以及返回字段间必须保留的逐行或逐路径对应关系。

除 `full_method_call_chain` 还可识别入口 API 外，其余调用类 `query_shape` 都以方法为锚点。以 `ts-...-service` 微服务为锚点、查询 REST 调用方或跨服务 API 对应关系时使用 `general`，不得套用方法上游可达、完整入口链或完整下游链；这类服务级事实仍须在一个查询中保持调用服务、调用方法、下游 API、目标 API 与入口方法的逐行对应。

## 消息通信

- 查询消息发布方、路由、队列、消费者和两端服务角色。
- 查询完整消息路径及其中需要保持对应的路由条件。

## 规划边界

- 只规划用户问题需要获取的信息，不生成查询语句或答案。
- 输出 JSON 前先在内部完成三步检查，不输出检查过程：第一，逐项列出原问题要求的结果集合；第二，判断每个集合能否从原始锚点独立计算且不依赖其他集合；第三，确认拆分不会破坏同一记录、路径、消息路径、分组或字段间的事实对应关系。满足第二、第三步的多个并列集合必须分别规划，不得因为共享锚点、处于同一句话或没有“分别”二字而合并。
- 方法变更题同时要求“全部上游方法”“可达入口 API”“变更方法直接 REST 下游”时，三个集合都能从变更方法独立计算，必须拆成三个自包含子问题并重复方法锚点。例如“修改 InsidePaymentServiceImpl.pay 后，调用它的上游方法、可到达的入口 API 和远程下游服务分别是什么？”必须规划为：查询能够调用到 InsidePaymentServiceImpl.pay 的全部上游可达方法（`upstream_reachability`）；查询能够到达 InsidePaymentServiceImpl.pay 的入口 API，并返回 API 路径和 HTTP 方法（`reachable_entry_api`）；查询 InsidePaymentServiceImpl.pay 直接远程调用的 REST 下游服务（`direct_rest_egress`）。
- 服务题同时要求“公开 API”“REST 下游服务”“通过 REST 依赖它的上游服务”时，三个集合也能从该服务独立计算，必须拆成三个自包含子问题并重复服务锚点。例如“分析 ts-security-service 的公开 API、REST 下游服务，以及通过 REST 依赖它的上游服务”必须分别规划：查询 ts-security-service 的公开 API 路径和 HTTP 方法；查询 ts-security-service 直接访问的 REST 下游服务；查询通过 REST 直接依赖 ts-security-service 的上游服务。三个服务级子问题均使用 `general`。
- 不得把需要保持顺序或逐行对应的完整事实按返回列机械拆分：完整入口调用链、完整下游调用链、有序方法路径和完整消息路径必须各自保留为单一子问题；同一 API 的请求与响应字段、同一 REST 调用的调用方与目标字段、同一分组的维度与聚合值也必须留在同一子问题中。完整方法调用链是固定例外，必须按服务内、REST、MQ 三种独立视图拆分。
- 方法变更语境中的泛称“外部服务”固定解释为变更方法直接远程调用的下游服务，不是上游调用方所属服务；对应子问题必须明确写出该方向。
- 同一记录、同一路径、同一消息路径或同一分组中相互对应的信息必须作为一个检索意图保留；不要按返回列、属性或关系端点机械拆分。
- 一个固定 API 的请求信息和响应信息、一个固定代码元素的归属和实现关系、一个发送服务及其下游服务的对应关系，都属于需要保留的完整答案形状。
- 分组维度与其聚合值必须在同一子问题中。例如，要求“每个目标服务的调用数”时，子问题必须同时要求目标服务和调用数，不能只问总数。
- 调用方向是不可省略的语义：明确区分“哪些方法调用 X”（上游调用者）与“X 调用哪些方法或服务”（下游目标）。
- 不得扩大或缩小原问题的范围：原问题未要求直接、间接、可达性或完整路径时，不得自行加入这些限定、调用链或额外关联信息；保留原问题已有的方向、范围和基数。
- 子问题必须把聚合的答案形状写完整：原问题同时包含对象维度和度量时，应写成“按每个对象给出度量”，不能将其简化成“总数是多少”。
- 只有多个业务视角能够独立重算且不需要其他查询结果时，才拆成多个自然语言查询。每个子问题都必须重复固定对象、方向、条件、分组和完整返回语义。
